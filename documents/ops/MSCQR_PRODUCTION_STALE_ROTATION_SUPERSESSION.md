# Production stale-rotation supersession

Stale-rotation supersession is a two-phase production transaction. Omitting `--mode` fails closed.

## Prepare

Run `npm run stage-b:supersede-stale-rotation -- --mode prepare ...` from a clean protected-main checkout. Preparation authenticates the release-deployer identity, live ECS baseline, publication and Stage-B identities, then performs the existing ten version-pinned selector reads. It atomically reserves one replacement rotation ID before generating the private material journal under the fixed operator-owned `~/.mscqr/production-cutover/stale-rotation-supersession/<source>/<stale-rotation>/` directory. A retry authenticates and reuses that reservation and journal; it never derives a second ID or material set. A fresh matching `preparation.json` is reused byte-for-byte. An expired zero-write preparation is revalidated, archived under its fixed SHA-256 name, and reissued with the same reservation and journal; it requires a new independent authorization. Refresh is refused after any approved write or terminal receipt. Preparation emits a sanitized seven-write artifact and performs no `PutSecretValue` operation.

Dispatch `authorize-production-stale-rotation-supersession.yml` with the exact preparation bytes and file SHA-256. The protected `production` environment supplies the independent approval; the workflow produces the only authorization accepted by execution.

## Execute

Run the same CLI with `--mode execute`, the exact preparation file SHA-256, and the dedicated authorization workflow run ID and attempt. A caller-supplied authorization file is not accepted. Before it constructs or resolves production credentials, execution re-fetches protected main and rejects any staged, unstaged, or untracked repository substitution. It then downloads the sole unexpired authorization artifact through the read-only GitHub runner, authenticates its archive digest, exact workflow/repository/head/attempt/conclusion, and independently reconstructs the protected-environment approval from GitHub before reauthenticating the live topology and canonical material journal. Immediately before every new `PutSecretValue`, it rereads the canonical Stage-B backend state and requires exact lineage, serial, and raw-state SHA-256 equality with the approved preparation. No secret write can occur until these checks and the externally rooted authorization match the preparation, publication, journal and ordered seven-write plan.

Each write retains the existing deterministic `ClientRequestToken`. Immediately before write one, execution records an authenticated private start record bound to the external GitHub authorization provenance, preparation, plan, journal, publication and live state. A fresh zero-write start record resumes the same transaction and may attempt write one. That record never extends freshness: after expiry, only an authenticated non-zero prefix may write its remaining suffix; a zero prefix, missing start record, altered binding, or non-prefix topology fails closed. An expired zero-write start is retired before preparation refresh and is never bound to the new preparation epoch. The private material journal remains through initial dual-slot bootstrap, so a crash after write seven can finish that handoff without another write. Execution then writes a terminal receipt bound to the authenticated GitHub artifact provenance, preparation, write plan, journal, supersession evidence and rotation binding before deleting the journal. If the process dies after receipt creation, the next invocation authenticates those exact terminal files and may delete only the still-matching canonical journal with zero secret writes. A missing journal remains a terminal replay rejection; a forged receipt or substituted journal fails closed without deletion.

All ECS and Secrets Manager operations use the canonical sanitized release-deployer named-profile runner. Secret payloads reach `PutSecretValue` through stdin, never process arguments.

Never put the private material journal, secret payloads, or decoded secret values in GitHub inputs, artifacts, issues, logs, or source control.

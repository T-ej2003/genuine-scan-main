# Production stale-rotation supersession

Stale-rotation supersession is a two-phase production transaction. Omitting `--mode` fails closed.

## Prepare

Run `npm run stage-b:supersede-stale-rotation -- --mode prepare ...` from a clean protected-main checkout. Preparation authenticates the release-deployer identity, live ECS baseline, publication and Stage-B identities, then performs the existing ten version-pinned selector reads. It atomically reserves one replacement rotation ID before generating the private material journal under the fixed OS-account `~/.mscqr/production-cutover/stale-rotation-supersession/<source>/<stale-rotation>/` directory; caller-controlled `HOME` cannot redirect it. A retry authenticates and reuses that reservation and journal; it never derives a second ID or material set. A fresh matching `preparation.json` is reused byte-for-byte. An expired zero-write preparation is revalidated, archived under its fixed SHA-256 name, and reissued with the same reservation and journal; it requires a new independent authorization. Refresh is refused after any approved write or terminal receipt. Preparation emits a sanitized seven-write artifact and performs no `PutSecretValue` operation.

Dispatch `authorize-production-stale-rotation-supersession.yml` with the exact preparation bytes and file SHA-256. Before emitting authorization, the workflow independently resolves the exact successful `Production Green Stage B Images` run and its sole unexpired four-image artifact, verifies the GitHub archive digest, parses the canonical JSONL, validates the complete publication-identity report and its SHA-256 against GitHub metadata, and matches all four source-bound digests. The protected `production` environment supplies the independent approval; the workflow produces the only authorization accepted by execution. Execution repeats publication authentication. A zero-write expired preparation may be refreshed only after current topology is independently reauthenticated. Live-backend and Stage-B observations are rebindable only through a new preparation and approval. Source, publication, stale/replacement rotations, reservation, journal, predecessor identities, secret resources, and the seven-write plan are transaction-fixed; changing any of them requires a separate transaction.

## Execute

Run the same CLI with `--mode execute`, the exact preparation file SHA-256, and the dedicated authorization workflow run ID at attempt 1. Workflow reruns are not authority: a failed authorization run requires a new dispatch and independent approval. A caller-supplied authorization file is not accepted. Before it constructs or resolves production credentials, execution re-fetches protected main and rejects any staged, unstaged, or untracked repository substitution. It then downloads the sole unexpired authorization artifact through the read-only GitHub runner, authenticates its archive digest, exact workflow/repository/head/attempt/conclusion, and independently reconstructs the protected-environment approval from GitHub. After authorization resolves, it performs a fresh live ECS service/task-definition read rather than trusting the earlier cached response. Immediately before every new `PutSecretValue`, it rereads the live ECS identity, the canonical Stage-B backend state, all seven rotation-slot version topologies, and the three live predecessor topologies. Exact task definition/image, Stage-B lineage/serial/raw-state SHA-256, deterministic prefix, and predecessor equality are required. No later mutation is queued before its guard.

Each write retains the existing deterministic `ClientRequestToken`. Immediately before write one, execution records an authenticated private start record bound to the external GitHub authorization provenance, preparation, plan, journal, publication and live state. Any observed deterministic prefix, including all seven completed slots, requires that exact start record before continuation or terminalization. A fresh zero-write start record resumes the same transaction and may attempt write one. That record never extends freshness: after expiry, only an authenticated non-zero prefix may write its remaining suffix; a zero prefix, missing start record, altered binding, or non-prefix topology fails closed. An expired zero-write start is retired before preparation refresh and is never bound to the new preparation epoch. The private material journal remains through a strict read-only initial dual-slot handoff: this governed caller rejects missing resources and requires every complete payload to equal the approved journal/write plan instead of falling back to generic bootstrap creates/writes. ECS is fetched again before binding generation. Execution then writes a terminal receipt bound to the authenticated GitHub artifact provenance, preparation, write plan, journal, supersession evidence and rotation binding before deleting the journal. If the process dies after receipt creation, the next invocation re-proves the completed live seven-write transition, authenticates those exact terminal files, and may delete only the still-matching canonical journal with zero secret writes. A missing journal remains a terminal replay rejection; a forged receipt or substituted journal fails closed without deletion.

## Invariant timing

Protected source and loaded module bytes are immutable for one process after the clean-checkout preflight. GitHub run/artifact provenance and the publication artifact are immutable identities. Live ECS, Stage-B state, the seven secret slots, and the three live predecessors require a fresh per-write CAS. The deterministic AWS version IDs are the cross-process transaction prefix. Reservation, preparation, authorization, execution-start, journal, write-plan, evidence, binding, and receipt identities are transaction-bound local artifacts; terminal cleanup additionally re-proves the completed live seven-write transition before deleting private material.

All ECS and Secrets Manager operations use the canonical sanitized release-deployer named-profile runner. Secret payloads reach `PutSecretValue` through stdin, never process arguments.

Never put the private material journal, secret payloads, or decoded secret values in GitHub inputs, artifacts, issues, logs, or source control.

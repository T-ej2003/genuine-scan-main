# Production cutover operator credential handoff

Run the command emitted by `stage-b:prepare-cutover-runtime` from the protected-main checkout in a trusted interactive terminal. It must use the canonical launcher:

```sh
npm run stage-b:run-cutover-operator -- --mode prepare-overlap --config <private-runtime-config> --config-sha256 <runtime-config-sha256> --source-sha <full-protected-main-sha> --rotation-id <rotation-id>
```

The launcher requires standard input and output to be TTYs. For `prepare-overlap`, it reads only the exact verifier MFA device ARN (`arn:aws:iam::368992683803:mfa/mscqr-production-bootstrap-operator`) directly from `/dev/tty` with echo disabled. The serial is an IAM MFA device identifier, never a six-digit TOTP. It is never a command argument, shell assignment, file, evidence, or launcher output, and is removed from the launcher environment immediately after the child starts or fails.

Use the existing authenticated local AWS and GitHub operator session; do not run `aws configure` or place credentials in shell startup files. The launcher passes only the runtime environment needed for the governed child plus the verifier serial. Strict-onboarding administrator and tenant-canary email/password are not accepted by `prepare-overlap`. After the independently authorized overlap deployment reaches `VERIFIED_OVERLAP`, `stage-b:verify-overlap` collects those four values from `/dev/tty` with echo disabled and runs the strict onboarding probes through the inherited MFA-backed verifier session. It does not pre-collect any MFA code. The prepare-overlap child does not establish a release-deployer or verifier session. The verifier continuation rejects release-deployer or unrelated callers; it does not prompt for a second verifier session. Onboarding or tenant-canary MFA remains separate: if live onboarding returns `MFA_BOOTSTRAP`, the existing just-in-time controlling-TTY provider prompts at that point and immediately submits the code.

Before any Terraform or AWS preflight call or verifier MFA prompt, the launcher authenticates the clean canonical protected-main checkout against the config-bound operation tooling SHA using the same verifier as the child. The Terraform adapter uses that checkout as its working directory and module root. It checks the exact runtime source and rotation binding, matches live Terraform state to the hash and serial in the bound tfvars report, reads the live execution-role policy with the existing release profile, and creates a refresh-only targeted Terraform plan. The plan directory must be mode `0700`; the saved plan is checked twice and the owner-checked regular file is normalized to mode `0600` before reading it. State drift, unexpected resource mutations, and a no-op whose planned policy differs from live IAM fail closed. A restart may replace its own private saved plan only after authenticating the existing file. An exact policy no-op skips `terraform apply`; a real update still requires the reviewed plan and post-apply policy verification. These preflight AWS calls are read-only and do not replace source, authorization, CAS, or mutation checks in the child.

The generated child uses `scripts/aws/run-production-cutover.mjs --mode prepare-overlap`, rechecks the plan and live state, persists and authenticates overlap readiness, and stops before overlap deployment. A later independently authorized rotation-overlap workflow consumes that readiness, performs the one governed service deployment, uploads an authenticated receipt, and terminates at `DEPLOYED_PENDING_VERIFICATION`.

The pre-MFA plan is local and regenerable; it is not an approval or a durable completion record. On restart, the launcher repeats checkout, artifact, state, plan, and IAM authentication before prompting. The child independently repeats protected-checkout and production authorization checks. The inventory broker owns its immutable execution claim and durable completion receipt, the rotation coordinator owns its persisted state and fixture, and the readiness producer authenticates its written receipt. A failed or expired authorization must be renewed through its own producer; a changed Terraform state or policy must be investigated before retry. The final-mode Release Train and Release Gate remain separate governed handoffs.

The operator then runs `npm run stage-b:verify-overlap` with the same private runtime config plus the exact Release Gate run ID and attempt, from the inherited verifier session. That continuation authenticates the workflow receipt and the original prepared-state hash, then resumes an already-persisted verified successor without redeployment when the coordinator has completed atomically. Only successful runtime proof plus coordinator `--verify` reaches `VERIFIED_OVERLAP`; a failed or interrupted verifier never retries `UpdateService`, and neither intermediate state permits cleanup or onboarding.

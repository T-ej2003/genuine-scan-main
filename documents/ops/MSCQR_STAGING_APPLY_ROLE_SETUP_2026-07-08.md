# MSCQR Staging Terraform Apply Role Setup

Date: 2026-07-08
Scope: separate AWS identity for the first controlled staging Terraform apply.

This runbook does not authorize `terraform apply`. It defines the identity split
that must exist before a separate human apply approval can use the apply
wrapper.

## Identity Model

- Plan role: read/plan only. Continue using the existing staging plan role for
  `npm run plan:staging-terraform`, inspection, and post-apply read-only checks.
- Apply user: `mscqr-staging-apply-operator`.
- Apply role: `mscqr-staging-terraform-apply-role`.
- The apply user can only call `sts:AssumeRole` for the apply role by using
  `documents/ops/iam/MSCQR_STAGING_TERRAFORM_APPLY_OPERATOR_POLICY_2026-07-08.json`.
- The apply role is for staging Terraform apply only. Do not use it for plan
  generation, production resources, production DB work, deployment, RLS
  enablement, or routine inspection.
- Root credentials should be used only for initial bootstrap if no safer IAM
  administrator path exists. Record the bootstrap evidence, then return to the
  plan role for inspection.

## Bootstrap Steps

Use the AWS console or an approved IAM administrator workflow. Do not commit
access keys, temporary credentials, CLI profiles, Terraform state, plan
artifacts, or private tfvars.

1. Create IAM user `mscqr-staging-apply-operator`.
2. Attach only the operator policy template:
   `documents/ops/iam/MSCQR_STAGING_TERRAFORM_APPLY_OPERATOR_POLICY_2026-07-08.json`.
3. Create IAM role `mscqr-staging-terraform-apply-role`.
4. Configure the role trust policy to allow only
   `mscqr-staging-apply-operator` to assume it.
5. Attach a staging-only Terraform apply permissions policy to the role. Scope
   it to the reviewed staging API resources, `eu-west-2`, and account
   `368992683803`. Do not attach `AdministratorAccess`.
6. Configure a local AWS profile named with staging and apply markers, for
   example `<staging-apply-profile>`.
7. Verify the identity:

```sh
AWS_PROFILE="<staging-apply-profile>" \
AWS_REGION="eu-west-2" \
npm run check:staging-aws-apply-identity
```

The checker must return `allowed: true`, `arnType: "assumed-role"`, and
`classification: "staging-apply-role"` before the apply wrapper can proceed.

## Apply Wrapper Contract

The apply wrapper is blocked by default. It accepts exactly one saved plan path
under `.terraform-plans/staging/*.tfplan` and requires matching `.summary.json`
and `.txt` evidence generated by `npm run plan:staging-terraform`.

The wrapper refuses:

- Missing apply gates.
- Missing or non-apply `AWS_PROFILE`.
- Root, IAM user, plan role, wrong account, wrong region, production-looking
  role names, or role names without staging/apply/terraform markers.
- Raw `terraform apply` options.
- `destroy`, `import`, `state`, `refresh-only`, `-target`, and `-replace`.
- Non-zero destroy count.
- Unexpected change count.
- World-open ingress in plan text.
- `DATABASE_URL`, `REDIS_URL`, `postgres://`, `postgresql://`, or `redis://` in
  plan text.
- Production-looking names or domains in plan text.

## Exact Apply Command Shape

Use placeholders only in tickets, PRs, and chat:

```sh
set +x
AWS_PROFILE="<staging-apply-profile>" \
AWS_REGION="eu-west-2" \
MSCQR_STAGING_TERRAFORM_APPLY_ENABLED=true \
MSCQR_STAGING_TERRAFORM_APPLY_CONFIRM=MSCQR_APPLY_STAGING_TERRAFORM_ONCE \
MSCQR_STAGING_TERRAFORM_APPLY_EXPECTED_ADD_COUNT=38 \
MSCQR_STAGING_TERRAFORM_APPLY_EXPECTED_CHANGE_COUNT=0 \
npm run apply:staging-terraform -- ".terraform-plans/staging/<approved-plan>.tfplan"
```

After apply, switch back to the plan role for inspection, run the post-apply
runtime secret sync workflow, then force the staging ECS redeploy only through
its own explicit gate.

## CTO Recommendations

- Keep the apply role short-lived operationally. Disable or remove its access
  keys when the first controlled staging apply window is complete.
- Add a permissions boundary for `mscqr-staging-terraform-apply-role` before
  future applies so even policy drift cannot reach production-like resources.
- Move toward OIDC-based role assumption from a protected GitHub environment
  once the manual first-apply path is proven.

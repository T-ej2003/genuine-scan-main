# Fresh inventory after the expired October claim

The inventory task for source `ccf30139819c006236a4edc22b92bdd10ee627c3` completed, but its execution claim expired before an adoption proof was signed. Its operation key and the permanent failed-predecessor reservation remain historical records. This change permits one **new** inventory operation for rotation `rotation-20260913011819-98b062c4`; it does not recreate or reinterpret the expired claim.

The new operation needs a different protected-main source, a fresh signed Stage B approval with at least 22 minutes of remaining validity for the reviewed broker version, the exact existing inventory task definition and image digest, and a self-bound runtime config prepared with `--new-inventory-after-completed true`. The broker checks the permanent predecessor reservation and the absence of the expired claim, then atomically writes a distinct non-expiring reservation and a short-lived execution claim. A competing dispatch cannot pass that transaction. A process interrupted before completion can resume the **same** signed operation after the 180-second Lambda fence and within a 20-minute recovery window. Its stable ECS RunTask client token prevents a second task; the claim and task ARN must still match. Outside that window, or if the outcome is ambiguous, recovery fails closed for independent review.

After the read-only inventory task exits successfully, the broker atomically marks its execution claim succeeded and writes a non-expiring completion item in the existing DynamoDB replay table. The item binds the operation key, source, rotation, task definition, image, signed approval, task ARN, inventory output and digest. It has no TTL. The existing independent-checker adoption producer can later verify this item and KMS-sign a short-lived adoption proof even if the execution claim and stopped task have aged out. It never signs an absent or mismatched receipt. The operator consumes that proof through the existing no-broker adoption path.

The producer requires the independent checker signer and the root readback profile; the operator validates the continuation config path, embedded `rotationConfigFile`, SHA-256, manifest, and proof before prompting for MFA. A crash before the atomic completion write may retry the same immutable broker request only within the fenced recovery window; the DynamoDB transaction checks the permanent reservation, signed nonce, source and operation identity.

# Stage B exact refresh-only state reconciliation

This is a one-purpose production control-plane contract. It exists because five previously authorized runtime IAM policy corrections were later reconciled into Terraform source, while the Stage B state at lineage `4e438e59-8b8b-194d-030c-5ede0c26344a`, serial `104` retained ten stale provider observations.

It is not a generic Terraform-drift override. It accepts only the ten addresses in `scripts/aws/production-green-stage-b-state-reconciliation.mjs`, the exact serial-104 `bound_images` state update derived from the authenticated tfvars binding, only a refresh-only plan, and zero remote resource operations. Any source, Terraform root, state lineage/serial, plan hash, ticket, tfvars, binding, preflight, address, output, policy-value, or provider-state deviation fails closed.

The protected preparation workflow carries the saved plan and bound inputs as one authenticated, short-lived artifact. Authorization and execution accept only that exact preparation artifact and its single authenticated authorization artifact; no Terraform plan is accepted through workflow-dispatch input.

The ceremony has three separate phases:

1. `npm run stage-b:state-reconcile -- --mode prepare` creates the exact reviewed refresh-only plan and private preparation evidence using the canonical release-deployer session.
2. The dedicated `Authorize Stage B refresh-only state reconciliation` workflow obtains an independent `production` environment approval and produces a bound authorization artifact.
3. The dedicated execution workflow rechecks protected main, state lineage/serial, every bound input, and applies only the saved refresh-only plan. It then proves the refresh-only closure is clean and the remaining ordinary plan is exactly the separately governed Stage B task-definition and broker convergence captured during preparation.

The refresh-only authority and ordinary deployment authority remain separate. Preparation binds the complete remaining ordinary-plan topology and values so the state write cannot expose an unreviewed next plan. The refresh-only authorization cannot apply that ordinary plan. The later Stage B deployment still requires its own normal-plan validation and production authorization.

The regression fixture `scripts/tests/fixtures/production-green-stage-b-state-reconciliation-serial-104.json` is a sanitized projection of the Terraform 1.15.8 plan captured by failed preparation run `36629064806`. The state-reconciliation regression projects the exact pre-write topology observed in run `36655840875`: the ordinary plan repeats only the ten authenticated refresh reflections, and every corresponding ordinary resource action is `no-op` with live and source values equal to the authenticated successor. After the write, those reflections must be absent. The fixture retains the exact `bound_images` transition, pending ordinary resource and output changes, variables, and configuration expressions consumed by the validators. The recorded saved-plan and plan-JSON digests identify the production evidence, while the fixture itself is not an executable saved plan.

The authorization is one-shot for the state write: a successful reconciliation advances the exact serial CAS. If the state write commits but post-write verification or result publication is interrupted, the same authenticated execution may recover only from the exact successor serial by proving the clean refresh closure and the unchanged bound ordinary-plan topology; it performs no second apply. Any later serial, different lineage, source advance, changed saved plan, or changed ordinary plan fails closed. Relocation approval binds the path-independent logical artifact mapping and hashes; preparation and execution may therefore use different runner-private roots. Each phase still authenticates its own 0600 runtime files, while the saved refresh-only plan remains the exact approved binary and is applied without a replacement plan or execution var-file. The execution workflow never applies a normal plan.

An `apply` process error never proves that this authorization committed state. If the authoritative readback still equals the predecessor, the result records `state-write-not-committed`. Any different or unreadable readback is recorded as `state-write-outcome-ambiguous` with no clean-closure claim, and the workflow fails for independent investigation rather than attributing another writer's successor to this execution.

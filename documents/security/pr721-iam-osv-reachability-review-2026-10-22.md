## Hostile review of the production installer

The saved Terraform plan must include `phase3_iam_source_sha` equal to the freshly authenticated protected-main merge SHA. The input is a declared non-resource variable; Terraform records it in the binary plan without changing AWS resources. A pre-merge plan lacking it, or bound to the earlier source, fails before the installer acquires ownership. Tests cover missing and mismatched plan bindings as well as the live IAM action tuple.

Interrupted recovery can observe an installed audit policy before it is imported into Terraform state. In that case Terraform still plans `create`. The installer accepts that action only with the exact live target fingerprint, original S3 owner claim, and matching durable audit dispatch marker; it performs no second audit write. The plan is never applied. The operator imports the authenticated policy after installation, then requires a no-change state-convergence plan.

Before the frontend IAM write, the installer rereads the native-audit policy after the frontend dispatch marker and rejects deletion or drift. This closes the network interval between audit installation and frontend mutation. IAM has no atomic compare-and-swap across the two inline policies, so the operator must still exclude out-of-band IAM writers during installation.

The production CLI resolves Terraform from fixed installation paths, checks its resolved binary and mode, and executes it without ambient `PATH`, Terraform CLI options, or AWS credentials. It copies the supplied saved plan bytes to a private file, decodes that same copy, and reports the SHA-256 of those bytes. A replaced or stale original path cannot make the plan JSON differ from the reported digest.

Before any checkout or lineage check, the production bootstrap verifies `/usr/bin/git`, removes inherited `GIT_*` overrides, disables global and system Git configuration, pins the local worktree, disables Git filesystem monitors and replacement objects, rejects local replacement refs, and puts `/usr/bin` first in this process's `PATH`; its own lineage call uses `/usr/bin/git` directly. The protected-main SHA comes from the pinned, authenticated GitHub API, so local Git transport configuration cannot forge a fresh protected-main fetch. Local Git still checks the checkout state. This confines the trust change to the IAM bootstrap and leaves the sealed Stage B and RLS source contracts unchanged.

The actual CLI constructs the single-attempt AWS runner using the safelisted AWS binary, verifies a clean exact-main checkout, decodes the saved plan with an initialized private Terraform data directory, pins GitHub API calls to `github.com`, requires the unedited accountable-operator comment for the final PR head, and checks fresh MFA from the fixed non-root user. It rereads the authorization comment after MFA, before ownership and after each dispatch journal immediately before the IAM write. A fresh protected-main API read after MFA, before ownership, before each IAM journal and after each journal closes the longer interactive and S3 time-of-check gaps. The tests reject wrong source, ticket, caller, policy expansion, target hash, live predecessor, Terraform action tuple, GitHub host injection, PATH-shadowed AWS CLI, authorization revocation and protected-main drift. A changed live policy is checked again after ownership and immediately before its own dispatch.

The first installation requires the recorded predecessor and missing audit policy. A partial or completed installation requires the original private owner file, its exact S3 claim, and matching per-policy dispatch markers. Conditional S3 writes and IAM writes use one AWS CLI attempt. Each dispatch marker has a unique attempt ID: a lost response can continue only if readback matches that exact attempt; a competing attempt cannot consume it. A target that appears after the checkpoint reads is not accepted without this owner's marker. The predecessor is read again after journaling and just before `PutRolePolicy`, closing the longer S3 network interval against concurrent IAM drift. A lost IAM response is reconciled against exact live policy and durable journal state. If a prior dispatch left the predecessor live, the outcome remains unknown and no second write occurs. Missing, conflicting, or foreign owner evidence stops. MFA freshness is checked again for each new IAM dispatch. Completion requires both target live readbacks, both dispatch markers, and a write-once receipt. These checks cover stale plans, partial installs, concurrent terminals, lost responses, interrupted journals, and false-positive completion. They do not authorize a production run or infer that a remote IAM write has occurred. IAM has no conditional `PutRolePolicy` compare-and-swap; the operator must prohibit out-of-band IAM writers during the governed installation, and any conflicting readback stops recovery.

The local IAM checks use injected AWS/GitHub runners and cannot prove the live IAM checkpoint, the operator's future MFA session, or the post-merge Terraform state. The operator must generate a fresh plan from exact protected main after merge and stop if its actions, owner evidence, or live policy readbacks differ. Hosted exact-head audit must repeat the local OSV and browser-closure results before merge.

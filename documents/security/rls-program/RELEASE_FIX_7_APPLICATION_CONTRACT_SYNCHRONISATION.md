## Authoritative application chain

```text
validated frontend request
→ registered route or worker entry point
→ authenticated/session or public capability proof
→ controller/service adapter
→ reviewed repository function
→ exact PostgreSQL capability
→ FORCE-RLS policy and controlled owner
→ allowlisted response projection
```

Frontend roles, cached lifecycle state, route tenant identifiers, masked QR
codes, display codes, and query parameters never establish database
authority.

## Contract synchronisation completed

### Authentication and tenant scope

- Bearer and cookie authentication transport the same protected database
  capability contract.
- Active actor, MFA, refresh-token, invitation, and manufacturer-scope reads
  use RF1 functions rather than caller-installed tenant context.
- Manufacturer scope is returned by
  `app_rls.load_authenticated_manufacturer_scope(text,text,text,text,boolean)`.
  The function derives the actor from the authenticated capability, verifies
  active links, organization/licensee state, scope version, primary-link
  uniqueness, and bounded membership, and optionally queues attributed audit
  evidence atomically.
- Downstream route guards reuse the link IDs already revalidated during
  authentication; they do not repeat a protected link-table authority read.

### Administration, incident, notification, and audit paths

- Directory and administration controllers call the RF2/RF3 repositories.
- Incident and notification operations use the exact C03/B03 repositories and
  capability-bound request transactions.
- Incident email completion persists the actual provider sender selected after
  fallback in the same B03 completion boundary as delivery evidence. A failed
  delivery cannot be recorded as successfully completed.
- Audit, risk-analytics, dashboard, and batch operational reads use their
  reviewed projections rather than generic tenant context installation.

### QR, printing, and public verification

- QR archive output uses explicit reviewed entries; `archiver`,
  `readdir-glob`, vulnerable `minimatch`, and vulnerable `brace-expansion`
  are absent from the production tree.
- RF4 QR and RF5 printing routes retain immutable QR identity, exact
  lifecycle, connector, maker-checker, pagination, and rollback contracts.
- RF6 verification handlers consume one public-safe database projection.
  Removed multi-read verification helpers are not registered as fallbacks.
- Public verification route state removes signed bearer material from the
  browser URL after consumption.

## Lifecycle and error contracts

Printing remains database-authoritative:

```text
DRAFT → CODES_GENERATED → PRINT_ACKNOWLEDGED
→ PRINT_CONFIRMED → SAMPLE_VERIFIED → RELEASED
```

`FAILED` and `VOIDED` remain explicit terminal/error states. The API preserves
stable lifecycle reason codes such as `PRINT_ACK_REQUIRED`,
`PHYSICAL_CONFIRMATION_REQUIRED`, `SAMPLE_SCAN_REQUIRED`,
`MAKER_CANNOT_APPROVE`, and `INVALID_STATE_TRANSITION`; the frontend maps
these to customer/operator language and refetches authoritative state.

Public verification preserves the internal decision classes
`FIRST_SCAN`, `LEGIT_REPEAT`, `SUSPICIOUS_DUPLICATE`,
`BLOCKED_BY_SECURITY`, and `NOT_READY_FOR_CUSTOMER_USE` while returning only
the RF6 public-safe projection.

Database denials are mapped to stable authentication, authorization,
not-found, lifecycle-conflict, rate-limit, and internal-failure envelopes.
SQL text, policies, protected IDs, raw capabilities, and stack traces are not
returned.

## Router and redirect security

- `react-router` is pinned to patched `8.3.0`; the deprecated
  `react-router-dom` re-export is absent.
- React and React DOM are pinned to `19.2.7`, the minimum peer set required by
  Router 8.3.0.
- Internal return paths accept canonical same-origin relative routes only.
- Absolute, protocol-relative, encoded external, nested, and `javascript:`
  redirects are rejected.
- External support links remain a separate reviewed HTTP(S) allowlist.
- Router tests cover nested/deep routes, protected redirects, session expiry,
  signed-token consumption, browser history cleanup, 404 handling, and unsafe
  redirects.

## Dependency security and archive limits

- Frontend and backend production audits report zero reviewed high or critical
  advisories.
- CI runs the machine-readable audit policy independently for both production
  trees.
- An exception requires exact advisory/package identity, rationale, owner, and
  a future expiry; wildcards, stale entries, expired entries, and dev-only
  misclassification fail.
- The active QR archive path uses explicit entries only, deterministic safe
  names, bounded item and output sizes, streaming/backpressure, abort handling,
  and fail-closed error propagation. It does not glob the filesystem or emit a
  successful partial archive.

## Rollback

RF7 changes application code, lockfiles, reviewed SQL capability definitions,
exact grants/policies, generated artifacts, and tests. Rollback restores the
RF6 tree at `3718842f0414ed8eb61ff6ebdef861c8025d2a19` as one application/package
unit. The generated rollback drops only RF7-owned exact signatures and
policies without `CASCADE`; RF1–RF6 data and capabilities remain.

Router rollback requires the matching RF6 frontend bundle and lockfile.
Backend/frontend bundles must not be mixed across the boundary. Cache
invalidation uses immutable release assets. No staging or production rollback
is performed by RF7.

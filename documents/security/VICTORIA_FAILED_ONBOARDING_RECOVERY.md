# Fixed Victoria failed-onboarding recovery

`VICTORIA_FAILED_ONBOARDING_RECOVERY_V1` is source-bound to `victoria@mscqr.com` and `mscqr_production`. It can only prune an unfinished `SUPER_ADMIN` invitation identity. It never creates the replacement invitation; after recovery, an authenticated MSCQR `SUPER_ADMIN` must use `POST /api/auth/invite`.

## Dependency and audit proof

[`scripts/security/victoria-recovery-dependencies.json`](../../scripts/security/victoria-recovery-dependencies.json) lists each live Prisma foreign-key relation to `User` and `Invite`, its action/nullability, ownership meaning, classification, and treatment. The tests compare all current Prisma relations and historical migration constraint names. The migration history contains 59 User-FK occurrences (58 distinct live or retired names) and one Invite FK. The current model has 55 User references and one Invite reference; three historical User constraints are retired, and the PrintJob manufacturer FK was changed from `CASCADE` to `RESTRICT`.

Before account reads, the generated SQL verifies that both `User` and `Invite` still have RLS enabled and forced, then compares all 56 expected live FK tuples with PostgreSQL's catalog. The comparison includes child schema/table/column, parent schema/table/column, delete action, nullability, cardinality, and duplicate multiplicity. Missing, extra, duplicate, composite, re-targeted, changed-action, or changed-nullability constraints stop with `SCHEMA_DEPENDENCY_DRIFT`. Any non-internal trigger on a table the operation can delete stops with `SCHEMA_TRIGGER_DRIFT`, so an unreviewed side effect cannot run. Dependency counts return only table, column, classification, count, and removal eligibility. Business/shared/hard-blocker/unknown occupancy fails closed. Any refresh-token history or used/live password/verification token blocks cleanup; only expired unused reset/verification records may be removed. Any occupied immutable-audit FK also stops cleanup, so deletion cannot null an audit actor reference. Immutable audit tables are counted before and after; no audit row is explicitly deleted. The non-FK `AuditLog.userId` and `AuditLogOutbox.initiatingUserId` references remain untouched.

## Database capability

[`backend/src/rls-waves/session-c/c05/victoriaRecovery.template.sql`](../../backend/src/rls-waves/session-c/c05/victoriaRecovery.template.sql) defines the no-argument SECURITY DEFINER routine and cleanup routine. Its target and database are constants, the search path is fixed, `row_security` stays on, and the executor must use a SERIALIZABLE read-write transaction. It takes the same transaction advisory lock as invite issuance and locks the exact Victoria User and Invite rows before inspection, then makes the state decision and deletes within that transaction. Exact IDs are used for all deletion. CAS failure, row-count drift, audit-count drift, or any SQL error aborts the transaction. A repeat run after a successful cleanup returns the same verified clean terminal state when no activation evidence exists.

[`scripts/security/victoria-recovery-installation.mjs`](../../scripts/security/victoria-recovery-installation.mjs) renders the one-time installation SQL. It creates separate NOLOGIN function-owner and fixed LOGIN recovery roles, scoped column grants and policies, RDS IAM authentication, and only the exact procedure execute grant. Existing policies and table ownership are not changed. The installer grants its current schema-owner identity temporary `SET ROLE` membership only inside the installation transaction, transfers routine ownership, then revokes that membership and the function owner's schema CREATE before commit. The function owner has no login, no membership, and no BYPASSRLS. The execution routine revokes its own execute grant; a second cleanup routine revokes its execute grant after every normal result. The broker separately adds and removes the exact private RDS ingress rule around the single task.

The capability's installation artifact must be applied once through the production database schema-owner release control before the recovery workflow is run. Applying it is a controlled production database catalog change and is not performed by this implementation, CI, or the recovery task. After the run, the roles and scoped policies remain dormant so the capability is not silently re-created during the operation; no ordinary principal has membership in the owner role, and the fixed recovery login has no routine execute privilege. A later source-reviewed installation authorization is required to re-enable execution.

## Authorization and execution

The workflow runs only from protected `main`, requires the `production-victoria-recovery` environment approval, captures GitHub's actual approval event, and obtains a short-lived OIDC AWS role. It asserts no human IAM MFA context. A 10-minute KMS signature binds protected-main SHA, implementation checksum, operation, fixed target/database, immutable image/task-definition identity, environment, operator, actual approver evidence, workflow run, and nonce. The nonce is consumed with conditional S3 creation before the database call. Replayed or expired authorization fails closed.

The operator cannot run ECS tasks directly. A fixed Lambda broker validates the signed authorization and exact task definition, prevents a second recovery task from running, creates one tagged TCP/5432 ingress rule from the recovery task security group, and launches one Fargate task without ECS Exec. Ingress creation and task launch share one cleanup boundary, including a proven pre-launch failure and an ambiguous launch response. The broker revokes only a rule whose network tuple and complete `Operation`/`Target`/`AuthorizationNonce`/`SourceSha` tag identity match the cleanup attempt; a late attempt cannot revoke a newer attempt's rule. An exact ECS `STOPPED` event independently invokes the same cleanup path if the workflow runner disappears. Cleanup lists the fixed cluster by `startedBy`, then describes and locally verifies the family, source, nonce, tags, and status before stopping a task. It uses the recorded task ARN and the stop event to cover stopped tasks. Cleanup attempts persist versioned evidence before returning failure, and can be retried. The task uses only private endpoint egress plus UDP/TCP 53 to the VPC resolver. It has no shell command override, ports, secrets, public IP, Secrets Manager access, generic SQL input, or arbitrary target. It obtains a short-lived RDS IAM token from its task role.

## AWS and result contracts

The reviewed AWS contract is intentionally split by caller:

| Caller | APIs | Scope and required companion authority |
| --- | --- | --- |
| GitHub OIDC operator | ECR upload/describe, ECS `RegisterTaskDefinition`, KMS `Sign`, S3 authorization write/result read, Lambda alias invoke | Fixed repository, fixed task/execution roles through `iam:PassRole`, fixed keys/bucket prefixes, and fixed broker alias. The role has no `RunTask`. |
| Broker Lambda | ECS list/describe/run/stop/tag, EC2 describe/authorize/revoke, KMS `Verify`, S3 evidence read/write | Fixed cluster/family/task roles, `ecs:TagResource` only during `RunTask` with the three exact tag keys, fixed DB/recovery security groups, and fixed evidence prefixes. List/describe calls use the resource scope required by the AWS API. |
| Recovery task | RDS IAM connect, KMS `Verify`, S3 authorization read/nonce and result writes | Exact database resource ID/login, signing/evidence keys, and authorization/nonce/result prefixes. It has no Secrets Manager permission. |

Every S3 producer names the Terraform-managed evidence KMS key explicitly. The bucket policy rejects writes that omit or substitute that key, preventing an `aws/s3` encryption fallback.

The producer/consumer schemas are shared source contracts. Broker launch is exactly `operation/sourceSha/nonce/taskArn`; broker cleanup is exactly `operation/sourceSha/nonce/networkAuthorityRevoked/taskStopped`; persisted executor evidence is exactly `operation/sourceSha/authorizationNonce/status/reason/temporaryAuthorityCleanup/result`. A successful nested result must prove fixed target/database, no User, no active account, no verified email, no valid invite, preserved audit history, and either a completed prune or an already-clean repeat. Extra or misplaced boundary fields fail closed.

## Operator sequence and limits

1. Apply `infra/aws/terraform/production-victoria-recovery` through the protected production infrastructure approval path using the active database's existing VPC ID/CIDR, private subnets, private service endpoint security groups, RDS host/resource ID, and database security group. Publish the module outputs as the exact `VICTORIA_RECOVERY_*` repository variables referenced by the workflow. The module creates the isolated broker/task roles, fixed image repository, signing/evidence keys, evidence bucket, and broker; it does not install database objects.
2. Generate the installation artifact from the exact reviewed source SHA with `node scripts/security/victoria-recovery-installation.mjs --output /private/path/victoria-recovery-install.sql`, review its printed SHA-256 against the source commit, then apply it through the production schema-owner release control; retain the apply receipt. This is a separate privileged catalog action and is not performed by CI or the recovery task.
3. Run `.github/workflows/execute-victoria-onboarding-recovery.yml` from protected `main` and approve the `production-victoria-recovery` environment.
4. The retained executor result follows the shared envelope contract: operation/source/nonce/status/cleanup fields are top-level, and prune outcome fields are under `result`. The workflow validates the fixed operation, source SHA, nonce, target/database, `status=complete`, `result.pruneComplete=true`, and `temporaryAuthorityCleanup=true` before reporting success. Any other result is a hard stop; do not retry with the same nonce.
5. Separately authenticate as an MSCQR `SUPER_ADMIN` with fresh required step-up and issue exactly `POST /api/auth/invite` for `victoria@mscqr.com`, role `SUPER_ADMIN`.
6. The operation revokes both routine grants in the database transaction; the broker removes the exact RDS ingress after the task stops. Retain the evidence and installation receipt. The LOGIN and owner roles/policies remain dormant: the LOGIN has no table grants or routine EXECUTE, the owner has no login or role members, and network ingress is absent. A later schema-owner maintenance can remove those catalog objects after evidence retention requirements are met.

After the clean result and replacement invitation are verified, decommission the Victoria-specific execution plane in a separately reviewed maintenance change: disable the protected recovery environment/workflow, remove its repository variables, Lambda/event rule, ECS/IAM roles, recovery security group, and ECR repository, then drop the fixed database routines, policies, and roles through the schema-owner release control. Preserve the versioned evidence bucket, evidence KMS decrypt path, CloudWatch logs, and database audit records for the required retention period. None of those decommission steps changes the shared GREEN executor or normal deployment primitives.

Production execution, capability installation, and invitation are intentionally not performed by this source change. Tests are source-level and do not connect to production. PostgreSQL catalog execution, AWS integration, Terraform provider validation, protected-environment CI, and reviewer approval remain required before calling the operation ready to run.

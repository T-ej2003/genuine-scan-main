The bootstrap operator also lacks these reads. Those local AccessDenied results are identity limitations and do not prove why the hosted verifier-launcher failed. The protected launcher policy lists the collector's read actions. No existing diagnostic workflow or durable failed-step artifact exposes the precise hosted failure.

A bounded diagnostic code is needed at the actual collector stage and, for AWS errors, at the exact AWS service/API operation. It must never print exception text, command arguments, secret ARNs, payloads, credentials, or connection strings. The failure remains fail-closed and cannot be retried as a successful authorization.

It has no runtime proof, overlap-ready time, or verified state. The original bytes and source identity must remain unchanged.

The backend rotation reader requires `state.sourceSha === config.sourceSha` and `state.overlapDeploymentSha === config.overlapDeploymentSha` before reading live slots. The saved config also has an `initialMigrationSourceAdvance.currentSourceSha` bound to 0e. A synthetic, non-production rehearsal showed that changing only the top-level state and config source fields fails in the real reader with `stale-supersession handoff source ancestry is not authenticated`. Updating that bridge in the synthetic config let the reader reach `overlap-deploy-required`, but the edited files were not signed or production-admissible. This is a structural compatibility check, not authorization to copy or relabel historical state. The overlap readiness producer, deployment adapter, verifier, and initial-activation Gate each bind the source, state hash, deployment SHA, rotation ID, image digest, and task identity. Accepting the old state in only one reader would create an unconsumable or forged downstream transition.

A complete successor must create a distinct state and fixture in a new private directory, bind the predecessor byte hashes and original manifest/receipt, authenticate protected ancestry and fresh current-source operation approval, read live slot/version identities, and require an exact current-source image authorization. The successor state must carry immutable predecessor provenance and be consumed by the existing preparation, readiness, runtime verification, and Gate readers. Every file write must be exclusive or idempotently verified; the old files cannot be overwritten. The process must fail closed on a missing approval, changed live slot, stale Terraform state, duplicate or concurrent invocation, or mismatched source/rotation/image. After merge, the release source remains 8c and the new protected-main SHA is only authenticated recovery tooling, following the repository's existing tooling/release split.

The production cutover control plane calls `produceRuntimeRotationInventory`, `rotationPrepare.run`, rotation Terraform convergence, and overlap task registration before it writes readiness. It does this even when a prepared state file exists. The repository has an authenticated completed-inventory adoption path with zero broker mutation, but `buildFreshInventoryAdoptionEvidence` requires the original and continuation configs to have the same source SHA. Its payload also binds the original operation key to the continuation source. That contract cannot adopt the completed 0e operation into 8c without a distinct signed cross-source predecessor field and corresponding reader changes. The saved 0e config has no `recoveryTooling` binding, so the operator on current protected main rejects it at checkout authentication. A safe implementation must authenticate completed-stage adoption at each consumer; adding a state-copy helper alone would still launch inventory and may register another task. A local prototype of that helper was discarded after this hostile review. No successor code or authorization is ready for production.

The 0e inventory completion receipt is not in the preserved local file tree. The existing adoption producer reads DynamoDB under a privileged reader, while a fresh read-only `GetItem` with the local release-deployer role was denied. The successor cannot treat the historical manifest or the prepared state as a substitute for the independently authenticated completion receipt. A protected, least-privilege receipt transport is required before cross-source inventory adoption can be proved without an AWS-root override. Live task definition `mscqr-production-rls-green-backend-candidate:32` has the expected immutable backend image digest, but differs from the canonical overlap definition in runtime fields and secrets; it cannot be adopted as an exact overlap registration.

`registerOverlapTaskDefinition` unconditionally calls `ecs:RegisterTaskDefinition` before it reads back the resulting ARN. Unlike the 12 governed registrations, this path has no durable intent/completion record or ambiguous-response reconciliation. A successor continuation that merely reruns the control plane could therefore register another revision after a lost response or process crash. The exact overlap task may legitimately need a first registration, but only through a governed registration operation with a durable identity, concurrency exclusion, and readback adoption. A source SHA change alone cannot justify another revision. This must be addressed before claiming restart-safe replay prevention.

## Downstream handoff

No final-mode Release Train or Release Gate may be dispatched until the restricted database catalogue result and source-bound overlap readiness are authenticated. A read-only execution manifest must classify completed ECS, IAM, broker and Terraform operations as adoption/no-op, and enumerate only unfinished mutations and fresh approvals. Application images remain reusable under the canonical image-impact report; the 8c verifier-only image does not change application image inputs.

The supported verifier path remains: protected 8c image and requirements artifact → restricted preparation → protected verifier launch → read-only PostgreSQL catalogue result → deployment eligibility. The failed preparation did not reach the launch. Its current log suppresses every internal exception, so a bounded collector-stage/API code is the smallest useful diagnostic change; the hosted root cause remains unknown until that correction runs under the dedicated OIDC role. A local release-deployer AccessDenied is not evidence that the hosted role was denied.

# Stopped connector upgrade certification

## Contract

The signed installer detects the existing AppId and keeps its installation directory. For a stopped installation, `Acquire` checks the old executable's Authenticode signer and timestamp, its `--version` output with overrides cleared, and its SHA-256. A published upgrade must match the target release's `certifiedUpgradeSources` record served by the pinned HTTPS backend; an unpublished certification candidate must match the exact backend permit before maintenance evidence can be issued. The registry version must agree but cannot establish eligibility. It then checks persistent identity, printer selection, startup configuration, and dispatch journal. It launches only the signed **target** connector in `--offline-existing-install` mode. That mode holds the local listener for browser pairing and device-key signatures; it has no gateway or direct-print worker and rejects print routes. The installer never starts the old print service. A missing or conflicting state, launcher, signature, journal, or authorization stops the upgrade before replacement.

The manufacturer signs in on the same computer. The browser requests a backend maintenance fence before the device challenge. The backend accepts a historical signed session version only for the fenced registered device, then checks the certified source version and digest before protecting outstanding work or issuing authorization. It verifies a fresh signature from the existing Ed25519 key. The existing evidence issuer, guarded handoff, and transaction perform authorization, backup, replacement, post-install verification, and conditional fence release. A failed replacement restores the old binary **stopped**; it does not restart legacy print workers. Historical uncertain attempts remain blocked by the existing journal and database no-replay rules.

The SQL replacement is `backend/src/rls-waves/session-c/c02/connectorOfflineUpgradeDeviceBindingIncremental.sql`. It requires a separately reviewed production predecessor, owner/grant/RLS readback, transactional application, and post-migration verification. Do not install it merely because disposable PostgreSQL tests pass.

## Release boundary

The currently published 2026.11.19.1 manifest is `fresh-install-only`; it must stay that way. Normal upgrades require `certified-upgrade`. The new source-bound target is 2026.11.22.1. Its unpublished signed candidate may be used for **one controlled certification attempt** only after the release operator verifies the signed target run and attestation, the signed source installer and executable digest, and the offline qualification artifact. None of those artifacts alone constitutes real-upgrade certification.

The existing backend can then receive `CONNECTOR_UPGRADE_CERTIFICATION_PERMIT` as a deployment-scoped JSON value. It contains `attemptId` (a fresh random UUID), registered `manufacturerId`, `tenantId`, `agentId`, `deviceFingerprint`, `printerId`, `registrationId`, `sourceVersion`, `sourceRuntimeSha256`, `targetVersion`, `targetRuntimeSha256`, `targetInstallerSha256`, `targetSourceSha` (the signed connector's source SHA), `backendSourceSha` (the actual backend image source SHA), and `issuedAt`/`expiresAt` (UTC ISO timestamps, at most four hours apart). The backend verifies the target source and target digests against the reviewed unpublished candidate metadata, and both runtime source labels against `backendSourceSha`. Use only values read from the authenticated artifacts and trusted registration; never take the identity fields from installer input. Do not configure the permit before the matching signed candidate, qualification evidence, and compatible backend exist. Remove it after the attempt. No private key or manufacturer credential belongs in this value.

The installer verifies the old executable's Authenticode publisher, timestamp, version and AppId before pairing. A published `fresh-install-only` target is rejected immediately. For an unpublished target, the installer asks the backend to check the source digest, installer digest and registered-device identifiers against the single-device permit **before** it starts the offline bridge or creates a local fence marker. This preflight issues no authorization token; recent manufacturer authentication, trusted printer binding and fresh device proof are still required. A permit does not make the installer publicly downloadable or change the normal certified-upgrade gate. The durable fence, journal protection, single-use handoff and post-install checks still apply. A missing or expired permit fails before binary replacement.

For each future target, build and sign through the existing workflow, then add only individually certified `{version,runtimeSha256}` source records to that target's release metadata after real source-to-target evidence is reviewed. Verify the source executable digest from the authentic signed distribution or installed binary, certify the exact source-to-target pair on a disposable Windows installation and then on the real installation with operator approval. The existing signed fresh-install artifact cannot be relabeled as upgrade-certified. An absent source record leaves that version unsupported.

## Real Windows procedure (requires separate authorization)

1. Record the installed AppId, version, installation directory, signed executable digest, stopped process and listener, startup registration, agent ID, device fingerprint, public-key digest, selected printer, and backend registration. Confirm the 12 journal records are `ATTEMPT_RESERVED`; do not print, reconcile, or delete them.
2. Verify the target installer Authenticode signer and timestamp, exact SHA-256, release source, target version, and either the backend upgrade-scoped manifest or the exact controlled permit. Use `certify-existing-upgrade.ps1 -Stage Before` to write private local hashes; it does not run the old connector.
3. Double-click the signed installer as the installed Windows user. Sign in as the manufacturer admin in the opened browser, complete recent sensitive authentication, and let the installer acquire the bound authorization. No `MSCQRAUTH` file or command-line argument is supplied by the manufacturer.
4. Record installer result and transaction phase. Run `certify-existing-upgrade.ps1 -Stage After` with the same evidence directory and target digest. Verify one AppId/install directory, unchanged identity/key/printer/configuration and 12 journal hashes, new signed runtime/version, startup registration, authenticated backend session, and maintenance fence state.
5. Confirm no historical reservation was redispatched. If backend or local fence release is incomplete, leave printing paused and retain the transaction/evidence for recovery. Test eligible printing only with a newly authorized job and separate permission for physical output.

The helper proves local hashes and version only. The reviewer must also correlate the backend audit record for the same attempt, manufacturer, printer, device, signed target digest, maintenance authorization, post-install verification and fence state. Preserve the signed source/target provenance and before/after files together. Do not produce `upgrade-certification.json` or stage `certified-upgrade` publication until this real source-to-target evidence has passed review. A clean GitHub runner or a simulated fixture is not real existing-machine certification.
